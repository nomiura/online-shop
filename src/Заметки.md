<summary>22.09 nomiura - <span style="color:orchid">azure to read</span></summary>
По Wallet все-таки убрали @OneToOne и перешли на ID-based подход. Это распространённая практика в проде.

Что сделали:
В Wallet вместо ссылки на Account храним просто UUID accountId:

    `@Column(name = "account_id", nullable = false)
    private UUID accountId;`
Как работает связь 1:1:
Через уникальное ограничение в БД:

    `
    @Table(
        name = "wallets",
        uniqueConstraints = @UniqueConstraint(
        name = "uk_wallet_account",
        columnNames = "account_id"
        )
    )`
Это накладывает уникальность на колонку account_id в таблице wallets. 
База физически не даст создать второй кошелёк на тот же аккаунт. Если попытаться — ошибка duplicate key value violates 
unique constraint.

uk_wallet_account — просто имя ограничения. uk = unique key, wallet = таблица, account = колонка. 
По конвенции uk_<таблица>_<колонка>.

Где хранится связь:
Только в Wallet, потому что кошелёк не существует без аккаунта. В Account ничего не добавляем. 
Когда нужен кошелёк — идём в репозиторий:

    walletRepository.findByAccountId(account.getId());
Почему так делают:
Меньше связанность между Account и Wallet.
Нет неявных запросов от Hibernate (N+1, LazyInitializationException).
Контроль над тем, когда и какой запрос уходит в базу.
1:1 гарантируется на уровне БД, а не Java-кода — надёжнее.

Итого: @OneToOne убрали осознанно, связь 1:1 держится на @UniqueConstraint в БД, в коде ходим в репозиторий явно.
